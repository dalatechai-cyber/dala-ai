# V1 — the cut line

**The problem this document exists to solve:** every item in the architecture is
justified, so nothing is *obviously* cuttable. That is exactly how four months pass with
no customer message flowing and no revenue collected. This file draws the line, in
writing, so that "we should also…" has something to argue against.

Status: **plan, nothing built.** ROADMAP Phase 3.0 item 4.

**Updated 2026-09-01.** This file was written at 16:54 on 2026-08-31; D-009 closed at
19:34 the same day. The contingency it named under *What would make me wrong* — "if the
bake-off says Reception needs a model the ceiling cannot afford" — **fired.** See
[**The ceiling contradiction**](#the-ceiling-contradiction), which is now the one thing
standing between this plan and Track 2.

---

## V1 is done when this sentence is true

> **A real customer messages Matrix Eco Salon's Facebook Page, gets a correct Mongolian
> reply generated from the tenant's own knowledge base and sent on that tenant's own
> token, the cost is recorded against that tenant's ceiling before the call is made, and
> the founder can prove all four from the database.**

Not "the platform works." Four facts, each checkable. Everything below is in V1 if it is
required for that sentence and out if it is not.

Two commercial conditions ride alongside it, because a technically live tenant who
cannot be billed is not a business: the salon is **invoiced and has paid**, and the
Anthropic account has a **provider-side spend limit** set. Neither is code.

## What is in

One channel, one tenant, one direction, metered.

| Block | Why it cannot be cut |
|---|---|
| Webhook: raw-body signature verification, fast 200 | Without it Meta unsubscribes the Page under load, and an unverified endpoint is an open relay |
| **Per-entry** tenant resolution from `channel_identity` | The whole product. One POST can carry two tenants |
| The 200/500 asymmetry | An unknown Page must 200 (permanent — a non-200 risks losing the asset); an unreadable registry must 500 (transient — a 200 drops the event forever) |
| Durable queue + worker (QStash) | The ancestor's fast-ACK pattern, which is the one thing it got structurally right |
| `webhook_events` idempotency + lease | Meta retries. Without this a retry is a second bill and a second reply |
| Per-tenant token from `tenant_secrets`, decrypted per request | A module-scope cache is a cross-tenant credential leak on a warm lambda |
| Send to `/{page-id}/messages` | With `/me`, a token/tenant mismatch **succeeds** and posts as the wrong salon. There is no error to catch |
| Config tables + the prompt compiler + `config_snapshots` | The runtime must read a snapshot, not live tables, or a half-finished edit reaches a customer |
| The Ш1–Ш6 boundary gate + the output guard | The failure mode that costs the tenant money and Dalatech its reputation |
| Reserve→settle ledger with a hard ceiling | Reserve **before** the call. A ceiling checked after is not a ceiling |
| The compiled per-surface cap | The one control no query, cache or table can change |
| Telegram alerts | 80%, 100%, token expiry, unknown Page id, ledger unavailable |
| `catalog.sql` + `isolation.sql` in CI | Already written and green. Wiring them to CI is hours |
| Six CI checks | `no-store` guard · no `\b`/`\w`/`[a-z]` over user text · no `process.env.*CEILING|BUDGET|LIMIT` · env-example parity · no bare Supabase client · matcher sanity |

## The ceiling contradiction

**This blocks V1, and it is a commercial decision, not an engineering one.**

Two settled decisions were each correct on their own and contradict each other when
combined:

| | |
|---|---|
| **D-004** derives the spend ceiling from the *discounted floor* price | Reception in a full-team bundle is ₮200,000/mo, so at the 60% target margin the allowable model spend is **₮80,000 ≈ $22.86/month** |
| **D-009** chose the model by measurement and native-speaker review | Sonnet 5, measured at **~$0.0090 per reply** blended |

At the architecture's own assumed volume of **4,500 replies/month**, those two numbers
are:

```
ceiling                          $22.86 / month
measured spend at 4,500 replies  $40.50 / month     = 1.77x the ceiling
replies the ceiling actually buys 2,540             = 56% of the assumed month
```

**The ledger fails closed and reserves before the call** — that is rule 3 and it is not
negotiable. So the literal consequence of shipping both decisions as written is that
**Reception stops replying to Matrix's customers around day 17 of every month.** Not
degrades: stops. A tenant at its cap is refused before an Anthropic client is even
constructed, which is exactly what the design is supposed to do.

This is not a bug in either decision. It is the arithmetic they produce together, and it
was invisible until D-009 supplied the second number.

### What cannot resolve it

- **The prefix trim cannot.** [`prefix-trim.md`](prefix-trim.md) states its own ceiling:
  L1+L2 are ~16% of the prefix and move 29% margin into the low 30s. Closing a 1.77×
  overshoot needs ~44% off the per-reply cost. L3 scales with *tenant count*, not with
  this tenant's bill.
- **Re-running the bake-off cannot.** D-009 is closed on quality grounds that a cheaper
  model does not satisfy. Reopening it re-opens broken Mongolian in front of paying
  customers.
- **Quietly raising the ceiling cannot** — that silently sells Reception below the
  margin floor D-004 calls a **hard floor**, which is the one thing D-004 exists to
  prevent.

### The founder's options, and what each costs

None of these is mine to pick. Each is a different business, not a different
implementation.

| Option | What it means | What it costs |
|---|---|---|
| **A. Accept a lower margin on Reception** | Set the ceiling from an accepted margin (e.g. 0% at ₮200,000 → ~$57/mo) rather than from 60% | Reception becomes a loss-leader or a thin-margin product; the bundle economics carry it |
| **B. Sell against a volume band** | Price ₮250,000 for up to *N* conversations/month, overage billed or throttled | Needs a number for *N* and a written overage rule; ~420 conv/mo is where 60% still holds |
| **C. Raise the price** | The floor moves, and every ceiling with it | Untested against what a Mongolian SMB will pay; D-004 was set deliberately |
| **D. Raise the target margin's denominator** | Accept 60% across the *bundle* rather than per role | Analytics and Customer Care subsidise Reception; needs their real costs, and Customer Care has no transport yet |

**Recommendation: B, with A as the fallback.** B is the only one that keeps a hard floor
honest *and* keeps the ceiling meaningful — it makes the thing being sold finite, which
is what the ceiling already assumes. It also converts the failure mode from "the bot went
silent" into "the customer bought more", which is the direction a business wants its
limits to point.

**Until this is decided, Track 2.2 has no number to compile in.** The compiled per-surface
cap is deliberately a constant that no query or table can raise; writing it requires
knowing what it is. Everything before Track 2.2 is unaffected and can proceed.

## Which onboarding steps V1 skips

The checklist is ~41 numbered steps across ten phases. V1 executes all of Phases A, C,
D, E, F, G, H, I, J. It **skips or defers** these:

| Step area | V1 |
|---|---|
| Instagram channel binding, IG-Login rehearsal | **Skipped.** `auth_flavour='instagram_login'` stays out of the constraint until a step rehearses it |
| Comment-field subscription and enrichment | **Skipped.** DM-only, which also narrows App Review |
| Quality-review provisioning (`quality_review` capability, corpus) | **Deferred.** `tenant_roles` row exists at `off` |
| Analytics provisioning (`tenant_domains`, redirect key, baseline capture) | **Partly.** Register `tenant_domains` and mint links — clicks are cheap and the 3-month baseline can only be captured *before* launch, so it is not deferrable. The monthly job is |
| Probe-token proof-of-possession flow | **Manual.** A founder-run probe still satisfies `active_requires_probe_run`; the automated flow waits for #3 |
| `handoff_targets` + Telegram `/start` with the salon | **Not skipped.** Without it the handoff path has no destination |
| Consent bootstrap + opt-out phrase list | **Not skipped.** Cheap, and it is the gate the other sections forget |
| Retention scheduling (`ops.purge_expired`) | **Not skipped.** A retention promise you cannot honour is worse than none |

**Two steps are load-bearing and easy to skip under deadline pressure, and both are
enforced by CHECK constraints rather than discipline:** a tenant cannot go `active`
without a published config, and cannot go `active` without a passing probe run. If the
cutover step fails, that is the constraint working.
