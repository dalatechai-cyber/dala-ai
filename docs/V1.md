# V1 — the cut line

**The problem this document exists to solve:** every item in the architecture is
justified, so nothing is *obviously* cuttable. That is exactly how four months pass with
no customer message flowing and no revenue collected. This file draws the line, in
writing, so that "we should also…" has something to argue against.

Status: **plan, nothing built.** ROADMAP Phase 3.0 item 4.

**Updated 2026-09-01.** This file was written at 16:54 on 2026-08-31; D-009 closed at
19:34 the same day. The contingency it named under *What would make me wrong* — "if the
bake-off says Reception needs a model the ceiling cannot afford" — **fired**, and has since
been **resolved** by D-015 (a 400-conversation band). See
[The ceiling contradiction](#the-ceiling-contradiction-—-resolved-2026-09-01-d-015), which
also corrects an overstatement in how it was first written up.

---

## V1 is done when this sentence is true

> **A real customer messages Matrix Eco Salon's Facebook Page, gets a correct Mongolian
> reply generated from the tenant's own knowledge base and sent on that tenant's own
> token, the cost is recorded against that tenant's ceiling before the call is made, and
> the founder can prove all four from the database.**

Not "the platform works." Four facts, each checkable. Everything below is in V1 if it is
required for that sentence and out if it is not.

Two commercial conditions ride alongside it, because a technically live tenant who
cannot be billed is not a business: the salon is **invoiced and has paid**, and the
Anthropic account has a **provider-side spend limit** set. Neither is code.

---

## What is in

One channel, one tenant, one direction, metered.

| Block | Why it cannot be cut |
|---|---|
| Webhook: raw-body signature verification, fast 200 | Without it Meta unsubscribes the Page under load, and an unverified endpoint is an open relay |
| **Per-entry** tenant resolution from `channel_identity` | The whole product. One POST can carry two tenants |
| The 200/500 asymmetry | An unknown Page must 200 (permanent — a non-200 risks losing the asset); an unreadable registry must 500 (transient — a 200 drops the event forever) |
| Durable queue + worker (QStash) | The ancestor's fast-ACK pattern, which is the one thing it got structurally right |
| `webhook_events` idempotency + lease | Meta retries. Without this a retry is a second bill and a second reply |
| Per-tenant token from `tenant_secrets`, decrypted per request | A module-scope cache is a cross-tenant credential leak on a warm lambda |
| Send to `/{page-id}/messages` | With `/me`, a token/tenant mismatch **succeeds** and posts as the wrong salon. There is no error to catch |
| Config tables + the prompt compiler + `config_snapshots` | The runtime must read a snapshot, not live tables, or a half-finished edit reaches a customer |
| The Ш1–Ш6 boundary gate + the output guard | The failure mode that costs the tenant money and Dalatech its reputation |
| Reserve→settle ledger with a hard ceiling | Reserve **before** the call. A ceiling checked after is not a ceiling |
| The compiled per-surface cap | The one control no query, cache or table can change |
| Telegram alerts | 80%, 100%, token expiry, unknown Page id, ledger unavailable |
| `catalog.sql` + `isolation.sql` in CI | Already written and green. Wiring them to CI is hours |
| Six CI checks | `no-store` guard · no `\b`/`\w`/`[a-z]` over user text · no `process.env.*CEILING|BUDGET|LIMIT` · env-example parity · no bare Supabase client · matcher sanity |

## What is out, and when it comes back

Each of these is deferred with a reason, not forgotten. **None is a maybe.**

| Deferred | Returns | Why it can wait |
|---|---|---|

| **Volatile/stable prompt split** | With platform-shared caching, Phase 5 | Worth little at two tenants |
| **KEK *rotation* machinery** | When a rotation is actually needed | **Escrow is not deferred** — it is a 30-minute Phase 3.0 item and losing the KEK is unrecoverable |

| **Tenant-owner login** | Undecided (item 12) | Policies ship dormant. Telegram is already the channel to this person |
| **Retrieval / embeddings** | Per-tenant trigger | `0002` exists; `app.search_kb()` ships in `0001` so nobody hand-rolls a vector query outside a tenant scope |
| **Billing automation** | After tenant #2 | For tenant #1 a bank transfer and a `paid_through` date is a fine answer — **say so rather than leaving it undesigned** |

## The ceiling contradiction — RESOLVED 2026-09-01 (D-015)

**Resolved by the founder: Reception is sold against a band of 400 conversations/month.**
Kept here rather than deleted, because how it was found and how it was mis-stated are both
worth keeping.

### What it was

Two settled decisions were each correct alone and collided when combined:

| | |
|---|---|
| **D-004** derives the ceiling from the *discounted floor* | ₮200,000/mo at a 60% target margin → **$22.86/month** allowable model spend |
| **D-009** chose the model by measurement and native-speaker review | Sonnet 5, **~$0.0090 per reply** blended |

At the design's own A7 (6 messages/conversation), $22.86 buys **2,540 replies ≈ 423
conversations**. Reception was being sold with no stated limit against a ceiling that
affords 423.

### The resolution

The ceiling does not move and D-004's formula is untouched. **What was sold moves**: 400
conversations/month included, with ~5% headroom under the 423 the ceiling actually buys.
Overage is the existing degradation ladder, not an invoice — billing overage is undesigned
and must stay that way while no revenue path exists. Full reasoning in
[`DECISIONS.md` D-015](DECISIONS.md).

### Correction: I overstated what happens at the ceiling

An earlier revision of this section said Reception *"stops replying to Matrix's customers
around day 17 of every month. Not degrades: stops."* **That was wrong**, and wrong in the
direction of alarm. [`05-spend-ledger.md` §5.7](architecture/05-spend-ledger.md) designs a
five-state ladder, and state 2 keeps the salon meaningfully alive: deterministic shortcuts
still answer location, hours and greetings, canned refusals still answer, the closure
message still answers, and anything needing the model gets the Mongolian handoff line to
7741-7777 **once per conversation**.

So the real failure is *"for part of the month the AI receptionist becomes an address-and-
hours bot that tells customers to phone"* — a genuine product problem and not what a salon
paid for, but not silence. I asserted the stronger claim without reading §5.7, which is the
same mistake as the composition-table misses: **a claim about a document, made without
reading the document.**

### And the overshoot rests on a number nobody has measured

The 1.77× that forced this decision assumed **750 conversations/month** — a guess, and one
the design does not agree with itself about. `05-spend-ledger.md` assumes **300–600 at ~5
replies each**:

| Real volume | Monthly spend | vs the $22.86 ceiling |
|---:|---:|---|
| 300 conv | $16.20 | 0.71× — comfortably under |
| 420 conv | $22.68 | 0.99× — exactly at |
| 600 conv | $32.40 | 1.42× — over |
| 750 conv | $40.50 | 1.77× — over |

### Measured 2026-09-01 — Matrix was already inside the band (D-016)

Six days of the ancestor's production logs: mean **60.5 replies/day → ~1,842/month, 41%
of the assumed 4,500.** Spend **$16.57/mo, 0.73× the ceiling, 71% margin** — clearing the
60% target. A8 = 750 is refuted; `05-spend-ledger.md`'s 300–600 was closer.

**The margin result is solid** (it depends only on the measured reply count). **The
conversation count is not** — it still divides by the unmeasured A7 = 6. Count distinct
PSIDs instead; the log line carries them.

The band stays at 400: the busiest day measured (94), sustained, is ~477 conversations —
outside it. Six days carries weekly shape and no seasonal shape, so the mirror phase's 14
days remains the measurement that sets the final number.

## Which onboarding steps V1 skips

The checklist is ~41 numbered steps across ten phases. V1 executes all of Phases A, C,
D, E, F, G, H, I, J. It **skips or defers** these:

| Step area | V1 |
|---|---|
| Instagram channel binding, IG-Login rehearsal | **Skipped.** `auth_flavour='instagram_login'` stays out of the constraint until a step rehearses it |
| Comment-field subscription and enrichment | **Skipped.** DM-only, which also narrows App Review |
| Quality-review provisioning (`quality_review` capability, corpus) | **Deferred.** `tenant_roles` row exists at `off` |
| Analytics provisioning (`tenant_domains`, redirect key, baseline capture) | **Partly.** Register `tenant_domains` and mint links — clicks are cheap and the 3-month baseline can only be captured *before* launch, so it is not deferrable. The monthly job is |
| Probe-token proof-of-possession flow | **Manual.** A founder-run probe still satisfies `active_requires_probe_run`; the automated flow waits for #3 |
| `handoff_targets` + Telegram `/start` with the salon | **Not skipped.** Without it the handoff path has no destination |
| Consent bootstrap + opt-out phrase list | **Not skipped.** Cheap, and it is the gate the other sections forget |
| Retention scheduling (`ops.purge_expired`) | **Not skipped.** A retention promise you cannot honour is worse than none |

**Two steps are load-bearing and easy to skip under deadline pressure, and both are
enforced by CHECK constraints rather than discipline:** a tenant cannot go `active`
without a published config, and cannot go `active` without a passing probe run. If the
cutover step fails, that is the constraint working.

## What would make me wrong

- **The 4–6 week estimate.** It assumes Meta App Review clears in ~20 days and that the
  Business-Portfolio token dance works first time. Neither is verified, and the research
  behind both is marked SEARCH-CORROBORATED at best because Meta's docs were unreachable.
- ~~**Track 3 assumes D-009 is settled.** If the bake-off says Reception needs a model the
  ceiling cannot afford, the plan pauses on a pricing decision, not an engineering one.~~
  **This happened, and is now closed.** The bake-off said exactly that; the founder
  resolved it with a conversation band (D-015). Recorded here rather than edited away,
  because a risk register is only worth keeping if it is scored afterwards — and this one
  scored: the risk was correctly identified in advance, and the response took one decision
  rather than a redesign.
- **Analytics being "deferred" assumes the booking-site query-parameter check comes back
  positive.** If it does not, Matrix is capped at Tier A + C forever and the first report
  is a different, smaller document.
- **The mirror phase assumes 14 days of lead time.** If the salon wants the bot switched
  next week, `prompt_cache_mode` ships on a guess and the cost model degrades.
